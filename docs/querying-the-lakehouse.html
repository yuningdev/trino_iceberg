Querying the Lakehouse

One SQL endpoint over every table in the cluster. Connect with DBeaver or the command line, then read and write tables in either of two formats — Iceberg or plain Hive — using the same SQL.

01

Every table has a three-part name

Trino reaches many storage systems at once, so a table name carries where it lives. Write all three parts whenever you are not sure which one is the current default:

iceberg.fmt_iceberg.events
catalog — which system schema — the folder inside it table — the table itself

The two catalogs holding real lakehouse data are iceberg and hive. They share the same storage and the same catalog service, so you query both from one connection — and can join across them in a single statement.

02

Connect with DBeaver

Create a new connection and pick the Trino driver — not Presto, which is the older, separate project. Fill in these values:

jdbc:trino://localhost:8080
Turn SSL off

This cluster speaks plain HTTP. If SSL is enabled on the connection, DBeaver fails with a handshake or connection reset error. Uncheck it under the driver's SSL tab before you test the connection.

Hit Test Connection. DBeaver will offer to download the Trino driver the first time — accept it. Once connected, the database navigator lists every catalog, and you can open a SQL editor against any of them.

03

Connect from the command line

From the project directory, open an interactive SQL shell:

make cli

You get a trino> prompt. Type SQL ending in a semicolon; use quit to leave. Run something without opening a shell: 

# a single statement
./scripts/trino-cli.sh --execute "SELECT count(*) FROM iceberg.fmt_iceberg.events"

# a whole .sql file, with results printed as tables
./scripts/run-sql.sh sql/41_format_evaluation.sql

Output comes back as aligned text by default. Add --output-format CSV, JSON or TSV when you want to pipe it somewhere.

Default catalog

make cli starts you in the iceberg catalog, so fmt_iceberg.events works on its own. Reaching anything else still needs the full name — hive.fmt_hive.events. To start somewhere else: ./scripts/trino-cli.sh --catalog hive --schema fmt_hive.

04

Find a table

Work down the three levels, then look at the columns:

SHOW CATALOGS;                          -- which systems can I reach
SHOW SCHEMAS FROM iceberg;               -- folders in one of them
SHOW TABLES FROM iceberg.fmt_iceberg;    -- tables in one folder

DESCRIBE iceberg.fmt_iceberg.events;     -- columns and types
SHOW CREATE TABLE iceberg.fmt_iceberg.events;  -- how it was defined

To search across everything instead of clicking down the tree, query the standard catalog views: 

SELECT table_schema, table_name
FROM iceberg.information_schema.tables
WHERE table_name LIKE '%event%';
05

Read data

Ordinary SQL — the format of the table underneath makes no difference to reads:

SELECT category, count(*) AS n, round(avg(amount), 2) AS avg_amount
FROM iceberg.fmt_iceberg.events
WHERE event_date >= DATE '1995-01-01'
  AND event_date <  DATE '1996-01-01'
GROUP BY category
ORDER BY n DESC;

Joining across catalogs

Because one connection sees every catalog, a single query can combine tables that live in completely different systems — here a lakehouse table and generated benchmark data: 

SELECT e.category, count(*) AS events, max(c.name) AS sample_customer
FROM iceberg.fmt_iceberg.events e
JOIN tpch.tiny.customer c ON c.custkey = e.user_id
GROUP BY e.category;
06

Create tables

Create a schema first — it becomes a folder in storage — then the table. Use the iceberg catalog unless you specifically need the older Hive layout. 

CREATE SCHEMA IF NOT EXISTS iceberg.my_schema;

CREATE TABLE iceberg.my_schema.readings (
    id          bigint,
    sensor      varchar,
    value       double,
    taken_at    date
)
WITH (partitioning = ARRAY['sensor', 'month(taken_at)']);

INSERT INTO iceberg.my_schema.readings
VALUES (1, 'north', 21.5, DATE '2024-03-01');

month(taken_at) is worth noticing: Iceberg derives the partition from the date column, so you filter on taken_at normally and it still skips irrelevant files. There is no extra column to populate or remember.

Build a table straight from a query with CREATE TABLE … AS:

CREATE TABLE iceberg.my_schema.recent_events AS
SELECT * FROM iceberg.fmt_iceberg.events
WHERE event_date >= DATE '1997-01-01';
Shared namespace

The two catalogs share one underlying catalog service, so a schema name means the same folder in both. hive.demo.events and iceberg.demo.events collide. Give each format its own schema — fmt_iceberg and fmt_hive are named that way for exactly this reason.

07

Changing rows: the one real difference

Reads are identical across both formats. Writes are not. Iceberg supports row-level changes; a plain Hive table can only be appended to or have whole partitions dropped. Everything in this table was run against this cluster:

Operation iceberg hive Notes
INSERT works works Appending is fine either way.
UPDATE works fails Hive: Modifying Hive table rows is only supported for transactional tables.
DELETE … WHERE id = 1 works fails Same error — Hive cannot delete individual rows.
DELETE … WHERE <partition> works partition only Hive can drop a whole partition, e.g. WHERE category = 'toys'.
MERGE works fails Upserts need Iceberg.
ADD COLUMN works works Both allow adding columns.
RENAME COLUMN works loses data On Hive the statement succeeds but the column reads back as NULL. See the warning below.
CREATE VIEW works works Views are stored in the catalog, not the data files.
Never rename a Hive column

It is the one operation here that fails silently. Trino reports success, and the next SELECT returns NULL for the renamed column — because Hive matches Parquet columns by name, so the old files no longer line up. Run on a one-row table:

hive → id 1, label NULL   ·   iceberg → id 1, label 'a'

Iceberg tracks columns by an internal id, so renaming is safe there. On a Hive table, add a new column and copy the values across instead.

So, on an Iceberg table, all of this just works:

UPDATE iceberg.my_schema.readings SET value = 22.0 WHERE id = 1;
DELETE FROM iceberg.my_schema.readings WHERE sensor = 'north';

MERGE INTO iceberg.my_schema.readings AS t
USING (VALUES (1, 'north', 23.1)) AS s(id, sensor, value)
   ON t.id = s.id
WHEN MATCHED THEN UPDATE SET value = s.value
WHEN NOT MATCHED THEN INSERT VALUES (s.id, s.sensor, s.value, current_date);

Many small writes leave many small files behind, which slows reads. Compact them when that happens: 

ALTER TABLE iceberg.my_schema.readings EXECUTE optimize;
08

History and rollback

Every write to an Iceberg table creates a snapshot, and the old ones stay readable. Hive tables keep no such record. Inspect history through the metadata tables — note the quotes, they are required: 

SELECT committed_at, operation, summary['added-records'] AS added
FROM iceberg.fmt_iceberg."events$snapshots"
ORDER BY committed_at;

Then read the table as it was at any point:

-- by snapshot id, taken from the query above
SELECT count(*) FROM iceberg.fmt_iceberg.events
FOR VERSION AS OF 9111639333786749600;

-- or by wall-clock time
SELECT count(*) FROM iceberg.fmt_iceberg.events
FOR TIMESTAMP AS OF TIMESTAMP '2026-11-08 09:45:00 UTC';

Other metadata tables follow the same "table$name" pattern:

Metadata tableWhat it tells you
$snapshotsEvery write, what it did, how many rows it added.
$historyWhich snapshot was current at which time.
$filesOne row per data file, with sizes and row counts.
$partitionsPartitions with row and file counts per partition.
$manifestsThe index files Iceberg uses to track data files.
$propertiesTable settings such as format and compression.
09

Views and daily rollups

A view is a saved query. It stores no data, so it is always current and costs a full scan every time you select from it. 

CREATE SCHEMA IF NOT EXISTS iceberg.reporting;

CREATE OR REPLACE VIEW iceberg.reporting.events_by_category AS
SELECT category, count(*) AS n, round(avg(amount), 2) AS avg_amount
FROM iceberg.fmt_iceberg.events
GROUP BY category;

A materialized view stores its result as a real table, so reads are cheap — but the answer is only as current as the last refresh. Use it for rollups that are expensive to compute and do not need to be up to the second. 

CREATE OR REPLACE MATERIALIZED VIEW iceberg.reporting.events_daily_mv AS
SELECT
    event_date,
    category,
    count(*)                AS event_count,
    count(DISTINCT user_id) AS unique_users,
    round(sum(amount), 2)   AS total_amount
FROM iceberg.fmt_iceberg.events
GROUP BY event_date, category;

-- without this it exists but holds nothing
REFRESH MATERIALIZED VIEW iceberg.reporting.events_daily_mv;

Query it exactly like a table. To find out whether what you are reading is current, ask Trino — it marks a view STALE by itself as soon as a source table is written to: 

SELECT schema_name, name, freshness, last_fresh_time
FROM system.metadata.materialized_views
WHERE catalog_name = 'iceberg';
Refreshes are scheduled outside Trino

Trino has no scheduler of its own, so REFRESH is driven by a companion service in this stack. events_daily_mv rebuilds every day at 08:00 Taipei time.

If you need it sooner, run make mv-refresh — or the REFRESH statement above — rather than waiting. Refreshing an unchanged view is harmless: it reports 0 rows and leaves the stored data untouched.

NeedUseWhy
Always-current numbers VIEW Recomputed per query; no staleness to reason about.
Fast dashboards over a big table MATERIALIZED VIEW Reads hit a stored table instead of rescanning the source.
A one-off extract to keep CREATE TABLE … AS A plain table — nothing refreshes it, which is sometimes what you want.

tpch is the quick way to get believable test data. Schemas are named by scale — tiny, sf1, sf10 — and the rows are generated on demand, so nothing is stored until you write it somewhere: 

CREATE TABLE iceberg.my_schema.orders_sample AS
SELECT * FROM tpch.tiny.orders;
11

Gotchas worth knowing up front

Metadata tables need double quotes

The $ makes events$snapshots an invalid bare identifier. Write iceberg.fmt_iceberg."events$snapshots". In the shell, the $ may also need escaping before it reaches Trino.

On Hive tables, partition columns go last

A CREATE TABLE … AS SELECT into the hive catalog must list the partition columns at the very end of the projection, in the same order as partitioned_by. Iceberg has no such rule.

Hive timestamps are milliseconds

The hive catalog stores timestamp(3). Writing a timestamp(6) value fails with Incorrect timestamp precision — cast it down first. Iceberg keeps microseconds.

Partitioned writes have a file-handle ceiling

Writing to more than 100 partitions at once fails with Exceeded limit of 100 open writers. Use a coarser partition — year(...) instead of month(...) — or load in batches.

Watch the Trino UI to see why a query was slow

localhost:8080 takes any username and shows query history and execution plans, including how much data each stage actually read. It does not accept SQL — use DBeaver or the CLI for that.
